## 3. 确认缺陷（禁止直接批量上线）

**P0-01：首批上限错误。** JS v1.3 第 315 行判断 `fm.fileExists(ledgerPath)`，空台账文件也会把批次从 3 条放宽到上限 400 条；对原始 158 条 Excel，模拟直接产生 **158 条**，违反首次最多 3 条的验收边界。

**P0-02：`COMMIT` 可伪造成功。** JS v1.3 第 275–289 行对任意 `COMMIT\n时间|数值` 只做数值/时间格式检查，不核对待提交事务、快捷取得的确认或 Apple 健康中的实际样本。模拟即使没写健康，也会产生“已登记”记录。这可能导致未来漏导。

**P0-03：失败重试可重复写入。** Scriptable 仅在整批 `COMMIT` 后记台账；HealthKit 循环写入中途出错时，之前成功的部分可能已保存，但台账仍为空。模拟无 `COMMIT` 直接重复运行会生成完全相同的输入批次。

**P0-04：协议标记不是一次性凭证。** `PING-V13` 固定返回 `READY|1.3`，不确认该批是否尚未处理；只要剪贴板上留有相同的合法数据，再启动快捷指令可能重复执行。未保存一次性批次 ID、准备状态或重试锁。

**P1-05：原始文件存在缺失时静默吞行。** 修改版 XLSX 删除 B2 或一整行后，JS 返回 157 条仍让用户确认；没有源行数/频率/缺口提示。重复时间且同值也会被 `Map` 静默合并；合成 CSV 中 10 分钟断档未产生提醒。

**P1-06：单位/时区未建立完整来源合同。** 源文件本身只有时间、血糖值两列，脚本假定 `mmol/L`，快捷指令使用 `detect.date` 解析未含时区的本地时间。若记录时间按 UTC+8，而设备使用 UTC+9，则同样的 `22:03` 实际时间戳可能相差 3,600 秒。属于高影响的**未实机验证风险**，不是已经证实设备写错。

**P1-07：没有写入后查询 Apple 健康。** 签名快捷指令包含 1 个 `health.quantity.log`，但没有读取/核对已保存样本动作。回执的含义只是“流程执行到回执步骤”，并不能证明 HealthKit 中每条记录的时间和值都正确。

**P2-08：剪贴板暴露与程序安全边界。** 每批血糖文本放在系统剪贴板；写入后没有自动清除。XLSX ZIP 解析按文件声称的解压大小分配内存，无明确总量/压缩比门槛。属于额外加固事项。

## 4. 业务闭环实际状态

应该只有一个入口：在 **Scriptable v1.3** 点脚本、选 **原始 XLSX**、预览并确认，Scriptable 才将解析的 `时间|mmol/L值` 交给 **「硅基血糖写入v1.3」快捷指令**；快捷指令写入 Apple 健康，并在验证成功之后登记去重。

当前代码实现了“文件解析 → 预览确认 → 构造交接 → 定义 HealthKit 写入动作 → 发送回执”的结构，但**没有证明最后三步在真实设备安全执行，也没有解决恢复的一致性问题**。不要以“代码已上传 GitHub”“已签名”“模拟成功”代替完整验收。

## 5. 修复与重新准入门槛

1. **冻结首轮**：显式 `verifiedFirstBatch` 状态，默认最多 3 条；空文件/老台账均不能解锁。必须先从 Apple 健康实际核对过的三条获得验收状态。
2. **批次事务化**：每批准备一次性 `batchId`，锁定时间、值和批次摘要，禁止重复运行正在写入或已写入的同一批；`PING`/`COMMIT` 必须绑定该批次。
3. **逐条成功验证与恢复**：增加真实 HealthKit 读回/核对，或采用按条记录成功后存储并以实际 HealthKit 读回作为去重依据；部分失败应进入 `NEEDS_RECONCILIATION`，不得自动从头重试。
4. **严格源数据检查**：表头、所有数据行、缺值、重复时间、5 分钟节奏、非预期时间范围、单位识别与压缩限制均生成显式检查结果；缺陷文件不得静默通过。
5. **时间合同**：明确硅基导出时区与 iPhone 时区对应关系，用至少 3 条跨日期、小时的数据在苹果健康里确认原始测量时间与记录值。
6. **真实 iPhone 验收序列**：3 条成功写入 → 从 Apple 健康读回 → 确认台账已登记 → 重新调用不再写入 → 中途失败仅重试缺失的记录。全链通过才开放 158 条历史导入。

**版本处理建议：保持 GitHub v1.3 标记“禁止批量写入”，不要再让用户下载相互不匹配的快捷指令版本。修复后应成对交付同名协议的 JS + 原生快捷指令，并出示手机端结果。**
